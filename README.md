# MemBomb

Учебная демонстрация исчерпания памяти (OOM) для портфолио по операционным системам и информационной безопасности.

**Автор:** Пётр Калинкин, Университет ИТМО.

Имя репозитория историческое. **По умолчанию это не бомба и не инструмент атаки.** Программа в одном своём процессе выделяет память до мягкого лимита, упирается в жёсткий потолок `HARD_CAP` и перед выходом всё освобождает. Флага «занять всю машину» нет.

## Предупреждение

Запускать **только в изолированной виртуальной машине** или одноразовом контейнере, где потерю сеанса не жалко. Не запускать на рабочей системе, на общей ВМ и на чужих компьютерах.

Даже с потолком программа пишет в каждую страницу, поэтому занятая память становится реальной ОЗУ, а не «пустым» резервом. На маленькой гостевой системе ставьте `-m` заметно ниже свободной памяти.

## Зачем это нужно

Три наблюдения, которые программа даёт увидеть, не доводя хост до отказа:

1. `mmap` (Linux) и `VirtualAlloc` (Windows) сначала создают виртуальный регион. Физическая страница появляется при первой записи — это demand paging. Поэтому программа пишет байт в каждую страницу, иначе свободная ОЗУ почти не меняется.
2. Мягкий лимит программы и лимит ОС — разные вещи. Процесс может остановиться на `HARD_CAP` или раньше, когда ядро вернёт ошибку выделения.
3. Защита стоит снаружи процесса. `ulimit` и cgroups (в Windows — квота задания и commit charge) обрывают выделение. Программа этот отказ не обходит и не продолжает цикл меньшими кусками.

OOM Killer в Linux — часть ядра, не отдельный демон: когда свободных страниц больше нет, ядро завершает выбранный процесс сигналом `SIGKILL`. Windows в той же ситуации чаще возвращает ошибку `VirtualAlloc` (`ERROR_COMMITMENT_LIMIT`, код 1455), и процесс остаётся жив. Эта лабораторная **не ставит цель** дойти до общесистемного OOM. Она останавливается на потолке или на первом отказе ОС и освобождает память.

## Безопасный режим по умолчанию

Режим SAFE включается сам. Отдельный ключ не нужен (`-safe`, если его передать, ничего не меняет).

| Параметр | Значение |
| --- | --- |
| Мягкий лимит | 64 МиБ, ключ `-m` |
| `HARD_CAP` | 256 МиБ, константа `HARD_CAP_MB` в `src/membomb.c` |
| Кусок | 4 МиБ, ключ `-c` |
| Пауза | 20 мс, ключ `-s` |
| После прогона | `munmap` / `VirtualFree` всей взятой памяти |

`-m` выше 256 обрезается до `HARD_CAP`. `-m 0` отклоняется: безлимитный режим выключен. Дополнительно программа не берёт больше половины `MemAvailable` (Windows: `ullAvailPhys`), даже если запрошено меньше потолка. Так прогон на тесной ВМ сам уменьшается и пишет, до какого объёма он снизился.

Если `mmap` или `VirtualAlloc` вернули ошибку, цикл на этом заканчивается. Размер куска вниз не уменьшается.

## Требования

- Компилятор C: `gcc` или `clang`. На Windows — MinGW-w64.
- Для самого прогона права администратора не нужны.
- Запись лимита cgroup обычно требует прав на нужную группу.

## Сборка

Linux:

```bash
make
```

Windows:

```bat
compile.bat
```

Вручную:

```bash
gcc -Wall -Wextra -O2 -o src/membomb src/membomb.c
```

## Запуск

Из каталога, куда можно писать CSV и SVG (не обязательно `src/`):

```bash
./src/membomb
./src/membomb -m 32 -c 4 -s 20
./src/membomb -h
```

Без аргументов программа берёт 64 МиБ, держит их около секунды, освобождает и пишет в текущий каталог `free_memory.csv` и `free_memory.svg`. На графике — память, которую затронул сам процесс: подъём до мягкого лимита, короткая полка, спад до нуля после освобождения. Колонка `free_mb` в CSV — оценка свободной памяти ОС (`MemAvailable` или `ullAvailPhys`). На занятой машине она не обязана упасть ровно на тот же объём: это оценка с учётом кэша, а не счётчик одного процесса.

Код выхода: `0` — мягкий лимит достигнут; `2` — раньше отказала ОС; `130` — пришёл сигнал, память всё равно освобождена; `1` — неверные аргументы или слишком тесный лимит.

## Как защищаться

Лимит снаружи сильнее любого потолка внутри учебной программы. Ниже — штатные механизмы, которые как раз и должны остановить такой процесс.

### ulimit

`ulimit -v` задаёт `RLIMIT_AS`, потолок виртуальной памяти процесса, в килобайтах:

```bash
ulimit -v $((48 * 1024))
./src/membomb -m 64
```

Запрос 64 МиБ больше потолка 48 МиБ. Ожидание: `mmap` вернёт ошибку, программа напечатает, что сработал лимит ОС, освободит уже взятое и завершится с кодом 2. В адресное пространство входит и сам процесс, поэтому затронутый объём будет немного меньше 48 МиБ. Машина целиком при этом не является целью опыта.

`ulimit -m` (резидентная память) на современном Linux часто не применяется. Рабочие рычаги — `ulimit -v` и cgroup.

### cgroups

В cgroup v2 файл `memory.max` — жёсткий потолок группы в байтах. Процессы в группе не получают память сверх него: выделение обрывается или OOM срабатывает внутри группы, а не на всём хосте.

```bash
sudo mkdir -p /sys/fs/cgroup/membomb-lab
echo $((64 * 1024 * 1024)) | sudo tee /sys/fs/cgroup/membomb-lab/memory.max
echo $$ | sudo tee /sys/fs/cgroup/membomb-lab/cgroup.procs
./src/membomb -m 128
```

`memory.high` — более мягкий порог: ядро начинает активнее отбирать страницы, не доводя группу до жёсткого отказа.

Через systemd тот же потолок выглядит так:

```bash
systemd-run --user --scope -p MemoryMax=64M -- ./src/membomb -m 128
```

### Windows

Предел процессу задают объектом задания (Job Object, `JOB_OBJECT_LIMIT_PROCESS_MEMORY`) и общим commit charge (ОЗУ плюс файл подкачки). Когда начислить commit нельзя, `VirtualAlloc` возвращает `NULL`, а `GetLastError()` равен 1455. Текст системы про «файл подкачки» означает отказ в commit, даже если на диске ещё есть место. Сохранённый пример такого отказа при квоте 64 МиБ лежит в [`docs/win_fail.txt`](docs/win_fail.txt).

## Чего программа не делает

- не отключает swap и не меняет `vm.overcommit_memory`;
- не повышает себе права и не трогает чужие процессы;
- не обходит `ulimit`, cgroup и квоту задания;
- не уменьшает кусок после отказа ОС, чтобы занять остаток машины;
- не оставляет выделенную память висеть после выхода.

## Ограничения

Потолок зашит в исходник. Снять его ключом командной строки нельзя: правка `HARD_CAP_MB` — это уже другая программа, и гонять её имеет смысл только в той же изолированной ВМ. Пример графика в `src/` снят командой `./src/membomb -m 32 -c 4 -s 40` и не является прогоном «до упора».
