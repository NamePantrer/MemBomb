# MemBomb

Лабораторная работа №2 по операционным системам: **выделение памяти страницами** до отказа,
снятие графика свободной ОЗУ, разбор OOM Killer в Linux и отказа `VirtualAlloc` в Windows.
Один исходник на C (`src/membomb.c`) собирается и под Linux (`mmap`), и под Windows (`VirtualAlloc`).

> ⚠️ Запуск без ограничений (`-m 0`) намеренно исчерпывает память. Делайте это в виртуальной
> машине или с квотой, а не на рабочей системе.

## Состав

| Путь | Назначение |
| --- | --- |
| `src/membomb.c` | Единственный исходник: выделение/касание страниц, замер свободной памяти, CSV/SVG |
| `src/free_memory.csv` | Пример ряда свободной памяти с прогона (Windows, 2 ГБ) |
| `src/free_memory.svg` | Построенный по этому ряду график |
| `Makefile` | Сборка под Linux (`membomb` и `membomb_raw`) |
| `compile.bat` | Сборка под Windows (MinGW `gcc`) |
| `docs/otchet.md` | Полный отчёт по лабораторной с результатами прогонов |

## Требования

- C-компилятор: `gcc` (MinGW-w64 на Windows) или `clang`.
- Для Linux-эксперимента с OOM — виртуальная машина и права `sudo` (для `swapoff -a`).

## Сборка

Linux:

```bash
make                 # соберёт src/membomb и src/membomb_raw
```

Windows (MinGW):

```bat
compile.bat
```

или вручную:

```bash
gcc -Wall -O2 -o src/membomb src/membomb.c
gcc -Wall -O2 -DMEMBOMB_RAW -o src/membomb_raw src/membomb.c
```

## Запуск

| Команда | Что делает |
| --- | --- |
| `./membomb` | Сразу «бомбит» до отказа, пишет `last_moments.csv` |
| `./membomb -m 2048 -s 8` | Выделить и коснуться 2048 МБ, шаг замера 8 |
| `membomb.exe -safe -m 2048 -s 8` | Безопасный сценарий: выделить, подержать, освободить, снять `free_memory.*` |
| `membomb.exe -safe -q 64 -m 0 -s 2` | Windows: квота Job Object 64 МБ → показать отказ `VirtualAlloc` без заморозки машины |
| `./membomb -plot` | Построить график из последнего CSV |
| `membomb_raw` | Тот же код без записи файлов (для «голой» ВМ) |

Ключ `-safe` включает «мягкий» сценарий с удержанием и освобождением; `-q N` в Windows ставит
квоту commit charge; `-m 0` снимает лимит (полное исчерпание).

## Что показывает лабораторная

- **Шаг = размер страницы (4096 байт).** И `mmap`, и `VirtualAlloc` создают лишь виртуальный
  регион; физический кадр появляется только при первом обращении (demand paging). Поэтому каждую
  страницу нужно «коснуться» — иначе свободная ОЗУ почти не падает.
- **График (Windows, ~32 ГБ):** при касании 2 ГБ свободная физическая память просела примерно на
  2 ГБ и полностью вернулась после `VirtualFree` — плато → спуск → hold → подъём.
- **Windows** не убивает процесс: при исчерпании commit charge `VirtualAlloc` возвращает `NULL`,
  `GetLastError()=1455` (`ERROR_COMMITMENT_LIMIT`, «файл подкачки слишком мал»).
- **Linux** при дефолтном overcommit не возвращает ошибку в `mmap`, а выбирает жертву по
  `oom_badness` и шлёт `SIGKILL` (OOM Killer — функция ядра, не демон). `swapoff -a` убирает
  «подушку» swap, чтобы OOM наступал сразу, а не после минут thrashing.

Полный разбор с командами, выводами и источниками — в [`docs/otchet.md`](docs/otchet.md).

## Что это не делает

- Не вредит системе за пределами своего процесса (в Linux процесс убивается, память возвращается).
- Не обходит квоты и лимиты ОС — наоборот, показывает, как они срабатывают.
- Не рассчитан на запуск на рабочей машине без лимита `-m`/квоты.
