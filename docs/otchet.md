# Лабораторная работа 2. MemBomb

**Дисциплина:** операционные системы  
**Факультет:** ИБ, ИТМО  
**Цель:** на практике увидеть разницу между виртуальной и физической памятью, снять график свободной ОЗУ, разобрать OOM Killer в Linux и отказ выделения в Windows.

## 1. Задание

1. Написать программу выделения памяти и заполнения её нулями с шагом, равным размеру страницы (`mmap`, `VirtualAlloc`).
2. Составить график свободной памяти.
3. Ознакомиться с работой OOM Killer в Linux.
4. Достичь сообщения о невозможности выделить память в Windows.

`swapoff -a` — обязательная подготовка Linux-эксперимента: без swap ядро быстрее упирается в нехватку физических страниц, а не в многоминутный thrashing файла подкачки.

## 2. Страницы, demand paging и зачем нужен «шаг»

И `mmap`, и `VirtualAlloc` по умолчанию создают **виртуальный** регион. Физический кадр ядро подкладывает только при первом обращении (page fault) — это demand paging / demand-zero pages.

Поэтому недостаточно вызвать `mmap`/`VirtualAlloc`. Нужно **коснуться каждой страницы**. Размер страницы на этой машине — **4096 байт** (`GetSystemInfo` / `sysconf(_SC_PAGESIZE)`). Цикл

```c
for (i = 0; i < n; i += page)
    *(volatile unsigned char *)(p + i) = 0;
```

пишет ноль в начало каждой страницы. Одного байта достаточно, чтобы PTE заполнилась и `GlobalMemoryStatusEx` / `MemAvailable` показали падение свободной ОЗУ. `volatile` не даёт компилятору выкинуть записи.

Куски по 4 МБ — только удобство: тысячи отдельных `VirtualAlloc` по 4 КБ были бы слишком медленными из‑за syscall и VAD. Педагогический шаг всё равно страница, не кусок.

## 3. Программа

Файл `src/membomb.c`, сборка: `compile.bat` или `gcc -Wall -O2 -o src/membomb.exe src/membomb.c`.

| Платформа | Выделение | Свободная память |
| --- | --- | --- |
| Windows | `VirtualAlloc(..., MEM_RESERVE \| MEM_COMMIT, PAGE_READWRITE)` | `GlobalMemoryStatusEx` → `ullAvailPhys` |
| Linux | `mmap(..., PROT_READ\|PROT_WRITE, MAP_PRIVATE\|MAP_ANONYMOUS)` | `/proc/meminfo` → `MemAvailable` |

Сценарий по умолчанию: `./membomb` сразу бомбит до отказа и пишет `last_moments.csv`. Для ВМ без файлов — `./membomb_raw` (тот же код, флаг сборки `MEMBOMB_RAW`). Кусок сам сужается к концу до одной страницы. После загрузки гостя: `./membomb -plot`.

Старый «безопасный» сценарий (лимит, удержание, освобождение, `free_memory.*`) включается флагом `-safe`.

`-q N` в Windows ставит квоту Job Object, чтобы получить отказ `VirtualAlloc` без вымораживания всей машины.

## 4. График свободной памяти (Windows 11, ~32 ГБ ОЗУ)

Команда:

```bat
membomb.exe -safe -m 2048 -s 8
```

Результат прогона:

- страница 4096 байт, всего ОЗУ ≈ 31862 МБ;
- выделено и затронуто **2048 МБ** (512 регионов по 4 МБ);
- свободная физическая память: **16509 МБ → минимум 14456 МБ → снова ~16505 МБ**;
- падение ≈ 2.05 ГБ, совпадает с объёмом касания;
- длительность ряда ≈ 21.5 с, 1076 точек.

Форма графика: плато → наклон вниз на время выделения → короткое плато (hold) → наклон вверх при `VirtualFree` → возврат к исходной свободной памяти. Файл: `src/free_memory.svg` (ряд — `src/free_memory.csv`).

Если бы страницы не трогали, виртуальный размер процесса вырос бы, а `ullAvailPhys` почти не изменился бы. Это главный измеримый факт лабы.

## 5. Windows: «невозможно выделить память»

В Windows **нет** OOM Killer. Учёт идёт по **commit charge**: лимит ≈ ОЗУ + файл подкачки. Когда лимит исчерпан (или процессу поставили квоту), `VirtualAlloc` возвращает `NULL`, процесс жив и получает ошибку.

Безопасный прогон (квота 64 МБ):

```bat
membomb.exe -safe -q 64 -m 0 -s 2
```

Фактический вывод:

```
Невозможно выделить память: VirtualAlloc(4194304 байт) вернул NULL, GetLastError()=1455
Сообщение ОС: Файл подкачки слишком мал для завершения операции.
ERROR_COMMITMENT_LIMIT (1455): система не может зарезервировать commit charge для региона.
Выделено и затронуто: 60.00 МБ в 15 регионах (дальше отказ ОС)
```

Код 1455 — `ERROR_COMMITMENT_LIMIT`. Текст «файл подкачки слишком мал» — штатное сообщение Win32, даже если подкачка на диске ещё есть: ядро не может начислить commit этому процессу.

Полный исчерпывающий опыт (сохранить работу, лучше уменьшить/отключить pagefile):

```bat
membomb.exe -m 0
```

Тогда отказ будет по глобальному commit limit, а не по квоте. Смысл тот же: Windows **отказывает в выделении**, Linux в той же ситуации чаще **убивает процесс**.

## 6. Linux: OOM Killer

OOM Killer — **не демон** и не процесс из `ps`. Это функция ядра (`out_of_memory` / `oom_kill_process`), которую вызывает аллокатор страниц, когда reclaim не дал свободных кадров и выделить память больше нельзя.

### 6.1. Почему `mmap` часто «успешен», а потом процесс умирает

По умолчанию `vm.overcommit_memory=0`: ядро **обещает** виртуальную память с запасом (overcommit). `mmap` возвращает адрес, errno нет. Физические страницы появляются только при записи. Когда записи съели ОЗУ (и swap, если он включён), ядро не возвращает ошибку в `mmap` — оно выбирает жертву и шлёт `SIGKILL`.

Это противоположность Windows.

`vm.overcommit_memory=2` запрещает overcommit: `mmap` начинает вести себя ближе к `VirtualAlloc` и может вернуть `ENOMEM` без OOM Killer.

### 6.2. Как выбирается жертва

Для каждого процесса считается `oom_badness` (в `/proc/<pid>/oom_score`, 0…1000):

- чем больше доля ОЗУ, тем выше балл;
- `oom_score_adj` ∈ [−1000, +1000] сдвигает оценку (`echo -1000 > /proc/<pid>/oom_score_adj` — процесс почти неприкасаем);
- root получает небольшую скидку.

Жертве — `SIGKILL` (не перехватывается). В журнале ядра:

```
Out of memory: Kill process 1234 (membomb) total-vm:... anon-rss:...
Killed process 1234 (membomb) ...
```

Смотреть: `dmesg -T | grep -i 'out of memory'` или `journalctl -k -b | grep -i oom`.

### 6.3. Зачем `swapoff -a`

С включённым swap система сначала начинает вытеснять страницы на диск. Это долго, UI «замирает», OOM может не наступить минутами. `sudo swapoff -a` убирает эту подушку: после исчерпания RAM сразу нехватка кадров → OOM Killer. Вернуть: `sudo swapon -a`.

### 6.4. Как провести опыт

В VM Linux, не на основной рабочей системе:

```bash
sudo swapoff -a
# терминал 2:
dmesg -w
# терминал 1:
./membomb -m 0
```

Ожидание: либо `mmap` вернёт «Невозможно выделить память» (если overcommit строгий), либо процесс исчезнет с `Killed`, а в `dmesg` будет запись OOM Killer. CSV в этом случае может не записаться — процесс убит до `write_csv`. Для графика на Linux безопаснее `./membomb -m 512`.

Полезно рядом:

```bash
grep -E 'MemAvailable|SwapFree' /proc/meminfo
cat /proc/$$/oom_score /proc/$$/oom_score_adj
```

## 7. Сравнение

| | Linux (default overcommit) | Windows |
| --- | --- | --- |
| Резерв виртуальности | часто успешен почти всегда | `MEM_COMMIT` сразу берёт commit charge |
| Исчерпание физической памяти | OOM Killer, `SIGKILL` | `VirtualAlloc` → `NULL` |
| Сообщение пользователю | `Killed`, строка в dmesg | «Файл подкачки слишком мал…» / ERROR_COMMITMENT_LIMIT |
| Можно ли «мягко» обработать | нет, SIGKILL | да, проверить возврат API |

И там, и там без касания страниц график свободной ОЗУ почти не двигается.

## 8. Выводы

1. Шаг, равный размеру страницы, нужен не «для красоты», а чтобы каждая страница получила физический кадр.
2. График свободной памяти на Windows при выделении 2 ГБ дал провал ~2 ГБ и полный возврат после `VirtualFree`.
3. OOM Killer — механизм ядра Linux при невозможности удовлетворить page fault; это не userspace-демон.
4. Windows в той же ситуации отказывает в `VirtualAlloc` (код 1455, текст про файл подкачки). Квота `-q` позволяет показать это сообщение безопасно.

## 9. Приложение. Планировщик (материалы курса)

Ссылки преподавателя про O(1) scheduler и CFS к выделению памяти относятся косвенно. Кратко, чтобы закрыть чтение:

- **старый O(1)** (2.6 до CFS): очереди по приоритетам, постоянное время выбора;
- **CFS** (`sched-design-CFS`): «виртуальное время выполнения» (`vruntime`), красно-чёрное дерево, цель — справедливая доля CPU, не FIFO;
- `sched(7)`, `perf sched`, `/proc/sched_debug` — инструменты наблюдения.

Связь с этой лабой: при нехватке памяти задачи не «несправедливо планируются», а стоят в I/O wait на swap. CFS тут бессилен — упираются в VM, не в CPU. Поэтому `swapoff -a` меняет картину сильнее, чем любая настройка планировщика.

Источники из задания: [CFS design](https://www.kernel.org/doc/html/latest/scheduler/sched-design-CFS.html), [sched(7)](https://man7.org/linux/man-pages/man7/sched.7.html), [IBM CFS](https://developer.ibm.com/tutorials/l-completely-fair-scheduler/), [Brendan Gregg, perf](http://www.brendangregg.com/perf.html#SchedulerAnalysis).
