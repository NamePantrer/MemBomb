# Отчёт. Учебный прогон MemBomb

**Автор:** Пётр Калинкин, Университет ИТМО.  
**Предмет:** операционные системы, наблюдаемый отказ в памяти.

Программа и порядок запуска описаны в [`README.md`](../README.md). Здесь только то, что видно на ограниченном прогоне, и чем отказ Linux отличается от отказа Windows. Общесистемный OOM эта работа не вызывает.

## 1. Что делает прогон

Процесс выделяет анонимную память кусками (`mmap` или `VirtualAlloc`) и пишет байт в каждую страницу. Пока страницу не тронули, физический кадр может не появиться: регион остаётся виртуальным. После записи страница учитывается в резидентной памяти процесса.

Потолок зашит как `HARD_CAP` (256 МиБ). Мягкий лимит по умолчанию — 64 МиБ. Пример ниже снят командой `./src/membomb -m 32 -c 4 -s 40`: 32 МиБ, кусок 4 МиБ, пауза 40 мс. Память затем освобождена, в конце ряда `allocated_mb` снова 0.

## 2. Ряд

Файл `src/free_memory.csv`, график `src/free_memory.svg` (по колонке `allocated_mb`).

На этом прогоне:

- затронуто ровно 32.00 МиБ, восемь кусков по 4 МиБ;
- удержание около одной секунды, затем симметричное освобождение;
- длительность ряда около 3.2 с;
- `MemAvailable` в это же время просел примерно на 12–15 МиБ, а не на 32.

Расхождение ожидаемо. `MemAvailable` — оценка ядра для всей системы, в неё входит кэш, который можно отобрать. Колонка `allocated_mb` считает только байты, которые затронул этот процесс. Для лабораторного графика взят второй ряд: он повторяет мягкий лимит и возвращается в ноль. Свободная память ОС остаётся в CSV, чтобы было с чем сравнить.

## 3. Где процесс останавливается раньше потолка

`ulimit -v` ограничивает виртуальное адресное пространство. Проверка вида

```bash
ulimit -v $((48 * 1024))
./src/membomb -m 64 -c 4 -s 0
```

заканчивается отказом `mmap` (`Cannot allocate memory`) раньше 64 МиБ. На прогоне с потолком 48 МиБ процесс успел затронуть 44 МиБ: остальное адресное пространство занято самим процессом. Код выхода 2, после отказа кусок не уменьшается, уже взятая память освобождается.

Тот же смысл у cgroup v2 `memory.max` и у systemd `MemoryMax=`: предел стоит на группе, а не на всей машине. Команды приведены в README.

## 4. Linux и Windows, коротко

| | Linux | Windows |
| --- | --- | --- |
| Выделение | `mmap` анонимного региона | `VirtualAlloc` с `MEM_COMMIT` |
| Пока страницу не трогали | физический кадр может не появиться | commit charge уже учитывается |
| Жёсткий внешний предел | `RLIMIT_AS`, `memory.max` | Job Object, общий commit limit |
| Отказ процессу | `mmap` → `ENOMEM` либо `SIGKILL` от OOM Killer, если память кончилась у системы | `VirtualAlloc` → `NULL`, код 1455 |
| Этот репозиторий | до общесистемного OOM не доходит | доводит только до отказа в своём лимите |

OOM Killer — функция ядра (`out_of_memory`), не служба из пользовательского пространства. Жертва получает `SIGKILL`. Windows процесс в той же ситуации обычно не убивает: API возвращает ошибку. Сохранённый текст такого отказа при квоте 64 МиБ — в [`win_fail.txt`](win_fail.txt).

## 5. Вывод

Касание страницы нужно, чтобы виртуальный резерв стал занятой памятью. Учебный процесс при этом остаётся внутри `HARD_CAP`, отпускает память и подчиняется внешнему лимиту. Защита от исчерпания — `ulimit` и cgroups (на Windows — квота задания), а не отсутствие демонстрационной программы.
